2. EXECUTIVE PROJECT OVERVIEW
================================================================================
Problem Statement PS-04: "Campaign Anomaly Alerting Without Alert Fatigue"

Digital advertising campaigns generate daily metric volatility due to auction
variance, predictable weekend day-of-week dips, and seasonal changes. Naive fixed-
threshold anomaly detectors (e.g., standard +/-20% flags) trigger overwhelming
volumes of false alarms, causing marketing teams to suffer severe "alert fatigue."
As a consequence, genuine operational catastrophes (such as broken conversion
tracking tags, account billing freezes, or runaway bid spikes) are overlooked.

CampaignGuard AI solves alert fatigue through a 5-layer detection architecture:
  1. Campaign-Specific Adaptive Median Absolute Deviation (MAD): Dynamic
     tolerance envelopes (14-day rolling window, K=3.5 sensitivity) tailored
     to each campaign's individual scale and noise profile.
  2. Persistence Filters: Multi-day sustained breach requirement to prevent
     single-day random spikes from triggering critical alarms.
  3. Domain-Specific Noise Suppression:
     - B2B Weekend Rule: Automatically suppresses alerts for weekend traffic drops
       on B2B lead generation campaigns (where B2B audience is naturally inactive).
     - B2B Revenue Zero-by-Design Rule: Suppresses revenue alerts for B2B campaigns
       because B2B campaigns generate sales leads, not direct online revenue.
     - Low-Volume Poisson Safeguard: Suppresses alerts when baseline conversions
       are < 4 and daily absolute difference is <= 2 (e.g. 1 vs 3 conversions).
  4. Deterministic Explainable Diagnostics: Every alert includes structured
     plain-English answers: "What changed?", "What was expected vs observed?",
     "Why was it flagged?", and "Recommended first operational check".
  5. Multi-Metric Incident Correlator: Groups related metric breaches into
     actionable root-cause incident categories (tracking failure, billing freeze,
     traffic surge, promotional event).

Benchmark Results over 3,600 daily observations (20 campaigns x 180 days):
  - Fixed-Threshold Baseline (+/-20%) : 284 alerts (9.2% precision, 100% recall)
  - Adaptive MAD                      : 174 alerts (43.1% precision, 100% recall)
  - CampaignGuard AI (Grouped Incidents): 110 incidents (-89.8% alert fatigue)

7.1 BUNDLED BENCHMARK DATASET (daily_campaign_metrics.csv)
--------------------------------------------------------------------------------
The project includes the official PS-04 dataset in two locations:
  - `data/daily_campaign_metrics.csv`
  - `public/data/daily_campaign_metrics.csv`

Dataset Dimensions & Statistics:
  - Total Rows       : Exactly 3,600 data rows (3,601 lines including header).
  - Campaigns Monitored: Exactly 20 campaigns (C01 through C20).
  - Date Range       : 2026-03-01 to 2026-08-27 (Exactly 180 continuous days).
  - Observations     : 20 campaigns x 180 days = 3,600 daily observations.
  - Total Columns    : 11 columns.

Actual Column Headers in daily_campaign_metrics.csv:
  1. date               (YYYY-MM-DD, e.g. 2026-03-01)
  2. campaign_id        (String identifier, C01 to C20)
  3. campaign_name      (Human-readable name, e.g. "Google | Brand Search")
  4. channel            (Ad platform: Google Search, Meta, TikTok, LinkedIn, etc.)
  5. vertical           ("ecommerce" or "b2b")
  6. landing_page_group (Destination grouping: LP-A, LP-B, LP-C, PDP)
  7. spend              (Daily spend in USD, float)
  8. impressions        (Ad impressions count, integer)
  9. clicks             (Clicks on ad, integer)
  10. conversions       (Purchases for ecommerce, leads for b2b, integer)
  11. revenue           (Revenue in USD, float; always 0.0 for b2b campaigns)

--------------------------------------------------------------------------------
7.2 REQUIRED CSV SCHEMA & COLUMN SPECIFICATIONS
--------------------------------------------------------------------------------
When uploading a custom CSV file via Settings (/settings), the client-side
validator checks the file against these exact constraints:
  - File Extension   : Must be `.csv`
  - File Content     : Must not be empty; must contain at least 1 header and 1 data row.
  - Required Columns : The header MUST contain the following 5 columns (case-insensitive):
      1. campaign_id
      2. date
      3. spend
      4. clicks
      5. conversions

Optional Recommended Columns:
      6. campaign_name
      7. channel
      8. vertical
      9. landing_page_group
      10. impressions
      11. revenue

--------------------------------------------------------------------------------
7.3 CUSTOM CSV UPLOAD & VALIDATION BEHAVIOR
--------------------------------------------------------------------------------
How Custom CSV Upload Works in the Application:
  1. Navigate to Settings (/settings) -> "Dataset Telemetry & Custom CSV Upload".
  2. Click "Choose File" and select any valid `.csv` file.
  3. The browser's native `FileReader` API immediately parses the header line.
  4. If required columns are missing: An amber warning alert is shown:
     "Validation failed. Missing required columns: [missing list]. Existing working dataset preserved."
  5. If required columns are present: A green success badge is shown:
     "Validation successful! Verified [N] records across required marketing columns. Ready for ingestion."

--------------------------------------------------------------------------------
7.4 ACTIVE DATASET CONFIRMATION VS IN-BROWSER VALIDATION
--------------------------------------------------------------------------------
IMPORTANT CLARIFICATION FOR EVALUATORS:
  - The custom CSV upload component in Settings performs INSTANT CLIENT-SIDE
    SCHEMA VALIDATION.
  - Validating a CSV in the browser DOES NOT overwrite the active in-memory
    3,600-row telemetry dataset or recalculate dashboard charts.
  - How to confirm this behavior:
    1. Upload a custom CSV with the required columns. Notice the green success
       message indicating successful schema validation.
    2. Navigate to Overview (/) or Campaigns (/campaigns). Observe that the
       displayed metrics, 180-day charts, and 174 alerts continue to reflect the
       official bundled benchmark dataset.
  - Architectural Rationale:
    Protecting the active dataset from arbitrary client-side file replacements
    ensures that incomplete or uncalibrated CSV uploads do not break mathematical
    envelope models, navigation links, or pre-computed benchmark comparisons.
  - In a full production deployment with a backend, validated CSVs are submitted
    to the `POST /api/dataset/upload` endpoint for server-side processing.

--------------------------------------------------------------------------------
7.5 OFFLINE PRE-PROCESSING SCRIPT (scripts/processDataset.js)
--------------------------------------------------------------------------------
The repository includes an offline Node.js compilation script:
  `scripts/processDataset.js`

Purpose:
  This script reads `daily_campaign_metrics.csv`, calculates 14-day rolling
  median absolute deviations (MAD) for each campaign, applies persistence and
  noise-suppression filters, and compiles the result into the TypeScript data
  module (`src/data/challengeDataset.ts`).

Dependencies:
  Uses ONLY Node.js standard library modules (`fs` and `path`). No extra npm
  packages are required.

Note for Developers:
  The script contains development paths. If re-running, ensure relative paths
  point to the current project's `data/daily_campaign_metrics.csv` and
  `src/data/challengeDataset.ts`.

--------------------------------------------------------------------------------
8.1 STANDALONE CLIENT-SIDE EXECUTION (DEFAULT)
--------------------------------------------------------------------------------
CampaignGuard AI is architected as a standalone single-page application.

    incidents, and model evaluation runs are bundled directly in the frontend.
  - Evaluators do NOT need to install Python, run Uvicorn, or set up a database.
  - The application works with 100% functionality out-of-the-box.

--------------------------------------------------------------------------------
8.2 OPTIONAL FASTAPI API CONTRACT & ENDPOINTS
--------------------------------------------------------------------------------
If an evaluator or developer provides an external FastAPI backend, the frontend
is equipped with `ApiClient` (`src/services/apiClient.ts`) ready to interact
with these REST endpoints:

  1. GET  /api/health
     Returns: `{"status": "connected", "version": "1.0.0"}`
     Used for the heartbeat badge in Settings.

  2. GET  /api/campaigns
     Returns: List of campaigns with summary KPIs.

  3. GET  /api/campaigns/:campaignId
     Returns: Detailed campaign telemetry and 180-day metrics.

  4. GET  /api/alerts
     Returns: List of flagged anomaly alerts.

  5. PATCH /api/alerts/:alertId/status
     Payload: `{"status": "investigating" | "resolved" | "dismissed"}`
     Persists alert triage state.

  6. GET  /api/incidents
     Returns: Grouped multi-metric operational incidents.

  7. GET  /api/evaluation
     Returns: Model evaluation runs, confusion matrix, precision/recall metrics.

  8. POST /api/evaluation/run
     Triggers backend anomaly detection calculation pipeline.

  9. POST /api/dataset/upload
     Multipart CSV file upload for backend ingestion.

--------------------------------------------------------------------------------
8.3 SWITCHING MODES IN APPLICATION SETTINGS
--------------------------------------------------------------------------------
To connect the frontend to a live FastAPI server:
  1. Start your FastAPI server on `http://localhost:8000`.
  2. Open CampaignGuard AI and go to Settings (/settings).
  3. In Section 4 ("FastAPI Backend Integration"):
     - Ensure the Base URL is set to `http://localhost:8000`.
     - Uncheck the box: "Use Synthetic Demo Data".
     - Click "Save Backend Configuration".
  4. If the backend is running, the status badge will update to "CONNECTED".
     If the backend is not running, the application gracefully falls back to the
     bundled dataset with console warnings.

9. COMPREHENSIVE TROUBLESHOOTING GUIDE
================================================================================

--------------------------------------------------------------------------------
ISSUE 1: 'node' or 'npm' is not recognized as an internal or external command
--------------------------------------------------------------------------------
Symptom: Running `node -v` or `npm -v` in terminal results in "command not found".
Cause  : Node.js is not installed, or its installation path is missing from PATH.
Fix    :
  1. Download and install Node.js (v18, v20, or v24) from https://nodejs.org/.
  2. Ensure the installer option "Add to PATH" is enabled.
  3. Completely restart your terminal or PowerShell window.
  4. Verify with:
     node -v
     npm -v

--------------------------------------------------------------------------------
ISSUE 2: Dependency installation fails during npm ci
--------------------------------------------------------------------------------
Symptom: `npm ci` fails with code EUSAGE or ENOENT.
Cause  : Missing package-lock.json or corrupted npm cache.
Fix    :
  1. Verify you are in the project root directory (`d:/CampaignGuard_AI`).
  2. Clear npm cache and retry with npm install:
     npm cache clean --force
     npm install
  3. If you encounter permission errors on Windows, run terminal as Administrator.

--------------------------------------------------------------------------------
ISSUE 3: Port 5173 is already in use
--------------------------------------------------------------------------------
Symptom: Vite starts on http://localhost:5174/ or displays "Port 5173 is in use".
Cause  : Another application (or previous Vite process) is using port 5173.
Fix    :
  - Option A: Simply open the new port displayed in your terminal (e.g. 5174).
  - Option B: Force a specific port:
    npx vite --port 3000
  - Option C (Windows): Find and kill the process occupying port 5173:
    netstat -ano | findstr :5173
    taskkill /PID <PID_NUMBER> /F

--------------------------------------------------------------------------------
ISSUE 4: Blank screen or loading spinner when opening the browser
--------------------------------------------------------------------------------
Symptom: http://localhost:5173/ loads a blank page.
Cause  : JavaScript error in browser, or stale local storage session.
Fix    :
  1. Open browser Developer Tools (F12) -> Console tab to inspect any errors.
  2. Clear application storage:
     - In DevTools -> Application tab -> Local Storage -> Clear all.
     - Also clear Session Storage.
  3. Hard refresh the page: Ctrl + Shift + R (Windows/Linux) or Cmd + Shift + R (Mac).
  4. Ensure you navigate to http://localhost:5173/login to re-authenticate.

--------------------------------------------------------------------------------
ISSUE 5: Uploaded CSV displays validation errors
--------------------------------------------------------------------------------
Symptom: Uploading a file in Settings shows "Missing required columns".
Cause  : The uploaded CSV header is missing one of the 5 required columns.
Fix    :
  - Open your CSV in a text editor and ensure the first line includes:
    campaign_id,date,spend,clicks,conversions
  - Ensure column names do not contain extra leading spaces or unusual quote characters.
  - Refer to `data/daily_campaign_metrics.csv` for the canonical format.

--------------------------------------------------------------------------------
ISSUE 6: Uploaded CSV does not change dashboard graphs or metrics
--------------------------------------------------------------------------------
Symptom: CSV passes validation, but Overview and Campaigns still show 3,600 rows.
Cause  : Working as designed. The in-browser upload provides instant schema
         validation but does not replace the active challenge dataset.
Explanation:
  - As documented in Section 7.4, client-side validation verifies file schema
    without overwriting the pre-compiled ground-truth dataset in browser memory.
  - To recompile the frontend dataset from a modified CSV, developers run the
    offline pre-processing script (`node scripts/processDataset.js`) or connect
    a live FastAPI backend.

--------------------------------------------------------------------------------
ISSUE 7: Backend status badge shows 'DISCONNECTED'
--------------------------------------------------------------------------------
Symptom: In Settings (/settings), the backend status displays "DISCONNECTED".
Cause  : Normal behavior. No local FastAPI server is running on port 8000.
Explanation:
  - This is expected and harmless in standalone mode.
  - The application automatically uses its bundled dataset and all features
    remain 100% operational.
  - If you are running an external FastAPI backend, ensure it is active and CORS
    is enabled for http://localhost:5173.

--------------------------------------------------------------------------------
ISSUE 8: Test suite or build fails
--------------------------------------------------------------------------------
Symptom: `npm test` or `npm run build` exits with non-zero error.
Cause  : Outdated node_modules or TypeScript compilation mismatch.
Fix    :
  1. Ensure you have installed dependencies cleanly:
     rm -rf node_modules package-lock.json
     npm install
  2. Run TypeScript check directly:
     npx tsc --noEmit
  3. Re-run tests:
     npm test
