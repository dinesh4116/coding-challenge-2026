# PS-04 — Campaign Anomaly Alerting Without Alert Fatigue (Spec)

Source: the hackathon problem statement (image shared in chat on 2026-10-10) plus the team's backend build brief. The problem statement is transcribed; the brief is condensed.

## Problem statement (transcribed)

*Time series · Threshold design · Production thinking*

**The situation.** We monitor a portfolio of live campaigns daily. Fixed-threshold alerting ("tell me if spend moves more than 30 percent") fires constantly on small campaigns where a single conversion swings the numbers, and stays silent on large ones where a 10 percent drift is a genuine emergency. Alerts that cry wolf get muted within a fortnight, and the muted channel is exactly where the real incident then goes unnoticed.

**What to build.** An alerting system over daily campaign metrics that flags genuine anomalies and stays quiet the rest of the time.

**Data we provide.** 180 days of daily metrics across roughly 20 campaigns, with a small number of real incidents seeded in: a broken conversion tag, a budget exhausted mid-month, a bid strategy change, and a seasonal shift that is not an incident at all.

**Minimum complete submission (the bar).** A system that reads the daily metrics, produces alerts carrying a plain-English explanation, and reports how many alerts it fired in total across the 180 days.

**Strong submission.**
- Alert bands are derived from each campaign's own historical volatility, not from one global threshold.
- Every alert carries a plain-English explanation of what changed, by how much, and against what baseline.
- You report your own precision and recall against the seeded incidents, including the ones you missed.

**If time is left.**
- Separate "something is broken" from "this is seasonality" and route them differently.
- Suggest a first diagnostic step for each alert type.
- Route alerts to a digest or as immediate notifications based on severity.

**What is really tested.** Production thinking. Reporting your own false-positive rate honestly is part of the grade.

## Backend brief (condensed)

- **Stack:** Python 3.11+, FastAPI, Uvicorn, pandas, NumPy, Pydantic, python-multipart, pytest. No heavy ML, external APIs or databases. Runs locally on Windows.
- **Layout:** `app/` (main, schemas, api/routes, services/{data_loader, features, detector, alert_manager, evaluation}), `tests/`, `data/demo_campaigns.csv`, `requirements.txt`, `README.md`.
- **Ingestion:** CSV upload only. Validate the file type, size, required fields and row limit. Use the dataset's real schema and normalize it to canonical fields (`campaign_id`, `date`, `impressions`, `clicks`, `spend`, `conversions`, `revenue`). Optional fields stay optional. Document how duplicates are handled. Invalid dates, non-numeric values and negative values never become misleading numbers. Uploads are not saved and row data is not logged.
- **Features:** CTR, CVR, CPA, ROAS (and similar) only when their inputs exist. A zero denominator produces null, never inf or NaN in the output.
- **Detector:** per campaign, past-only rolling window, median/MAD, a minimum history, safe handling of zero MAD, no future leakage, a low-volume guard, tolerance for missing days, configurable thresholds and severities, and detection in both directions. Each anomaly records the observed value, expected value, deviation or score, severity, reason, possible explanations, method and whether it can be suppressed. The score is a heuristic and must not be presented as a probability. Causes are framed as possibilities, never as confirmed.
- **Alert manager:** deduplication, grouping by campaign and by metric, a cooldown, suppression of repeats, escalation when severity rises, reopening after recovery, and separate counts for new, grouped/updated and suppressed alerts. Suppression stops notifications but keeps the evidence.
- **API:** `GET /api/health`, `GET /api/demo-data` (labeled synthetic), `POST /api/analyze` (multipart field `file`, optional window, sensitivity and cooldown). The response holds a summary, alerts, a timeline, warnings and an evaluation, with no NaN or Infinity. CORS allows `http://localhost:5173` by default and can be changed through an environment variable.
- **Evaluation:** precision, recall and F1 against ground-truth labels with a documented matching rule. With no labels, return nulls and give the reason. Disclose when the thresholds were tuned on the same data.
- **Required test cases:** a stable campaign; a conversion drop; a spend spike; a spend drop; insufficient history; a low-volume campaign; missing and malformed values; zero impressions, clicks or spend; repeats that should be grouped or suppressed; an escalation that the cooldown must not hide; a file with no valid records; and an official dataset sample if one exists.
- **README:** install steps for Windows PowerShell, the start command, the docs URL, endpoints, the CSV schema, how detection and suppression work, tests, limitations, and how to connect React.
- **Priority under a 3–4 hour limit:** server, then ingestion, detection, structured alerts, suppression, frontend contract, then tests and README.
